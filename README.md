# LinkUp — Сервис подбора кандидатов по интересам

Учебный проект на Go для продуктового трека **LinkUp**. Репозиторий
последовательно демонстрирует два этапа разработки: подбор кандидатов по
интересам и изменение состояния взаимодействия между пользователями.

## Лабораторная работа №1 — развитие пользовательских сценариев

### Цель

Реализовать сценарий **Discover**, который находит подходящих кандидатов для
пользователя на основе общих интересов. Логика отделена от чтения данных и
покрыта unit-тестами.

### Бизнес-правила

| Правило         | Поведение                                             |
| --------------- | ----------------------------------------------------- |
| Исключение себя | `subject` не может быть рекомендован сам себе         |
| Активность      | В выдачу попадают только профили с `Active: true`     |
| Общий интерес   | Нужен хотя бы один совпадающий интерес                |
| Уникальность    | Один кандидат появляется в результате только один раз |
| Изоляция данных | Входные профили не изменяются                         |

### Архитектура

Код разделён на чистую доменную логику, сервисный слой и in-memory
реализацию `ProfileReader`:

```text
linkup/
├── go.mod                     # Модуль проекта ([example.com/linkup](https://example.com/linkup))
├── cmd/
│   └── app/
│       └── main.go            # Точка входа: сборка зависимостей и демонстрационный запуск
└── internal/
    ├── discovery/             # Доменная логика и сервисный слой
    │   ├── model.go           # Доменная модель Profile
    │   ├── rules.go           # Чистая бизнес-функция Discover
    │   ├── service.go         # Сервисный слой и контракт чтения ProfileReader
    │   ├── rules_test.go      # Unit-тесты для чистой логики Discover
    │   └── service_test.go    # Unit-тесты сервисного слоя и обработки ошибок
    └── memory/                # In-memory реализация хранилища
        └── repository.go      # Реализация ProfileReader на данных в памяти
```

### Проверки

```text
go test ./internal/discovery
```

## Лабораторная работа №2 — реакции и взаимность

### Цель

Собрать законченный пользовательский путь: прочитать текущее состояние,
принять решение, сохранить изменение, корректно обработать повтор и показать
результат последующим чтением.

### Модель и правила

Сценарий использует `interaction.Service` и
`memory.InteractionRepository`. Пара пользователей идентифицируется одним
неупорядоченным ключом, а реакции в направлениях `source -> target` и
`target -> source` хранятся отдельно. Состояние `pending` означает Like,
а `matched` вычисляется после чтения обеих направленных реакций.

| Исходное состояние | Действие   | Результат                        |
| ------------------ | ---------- | -------------------------------- |
| отсутствует        | `pending`  | одна новая реакция               |
| `pending`          | `pending`  | no-op, новая запись не создаётся |
| `pending`          | `accepted` | `accepted`                       |
| отсутствует        | `accepted` | отказ до записи                  |

### Поток выполнения

1. Application-команда читает обе стороны взаимодействия.
2. Чистая функция `ProcessReaction` проверяет допустимость перехода.
3. `Save` вызывается только при изменении состояния.
4. Повтор уже выполненного действия возвращается как no-op.
5. Последующее чтение показывает актуальное состояние и взаимность.

Отсутствие записи трактуется как начальное состояние. Остальные ошибки чтения
и записи возвращаются вызывающему коду; ошибка записи не сообщает об успехе.

### Демонстрация

Запуск:

```bash
go run ./cmd/app
```

Demo показывает четыре шага: первая реакция, её повтор, ответ второй стороны и
его повтор. Ожидаемые значения `changed`: `true`, `false`, `true`, `false`;
на третьем и четвёртом шагах `matched=true`.
