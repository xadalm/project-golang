# LinkUp — учебный HTTP-сервис

Учебный проект на Go: подбор кандидатов по интересам, реакции и взаимность,
HTTP API и обязательная локальная зависимость Profile API. Профили и состояние
взаимодействий хранятся в PostgreSQL и доступны нескольким экземплярам сервиса.

## Лабораторная работа №1 — подбор кандидатов

### Цель

Сценарий **Discover** находит активных кандидатов, имеющих хотя бы один общий
интерес с пользователем. Чистые правила отделены от чтения профилей и покрыты
регрессионными тестами.

### Бизнес-правила

| Правило | Поведение |
| --- | --- |
| Исключение себя | Пользователь не рекомендуется самому себе |
| Активность | Выдача содержит только `Active: true` |
| Общий интерес | Достаточно одного точного совпадения интереса |
| Уникальность | ID кандидата не повторяется в результате |
| Изоляция данных | Правила не изменяют входные профили |

## Лабораторная работа №2 — реакции и взаимность

### Цель

Обработать действие пользователя, сохранить переход, корректно ответить на
повтор и показать состояние пары при последующем чтении.

### Модель и переходы

Одна неупорядоченная пара хранит две направленные реакции. `pending` означает
Like, а `matched` вычисляется по наличию `pending` в обоих направлениях.

| Исходное состояние | Действие | Результат |
| --- | --- | --- |
| отсутствует | `pending` | создаётся первая реакция |
| `pending` | `pending` | no-op, повторного сохранения нет |
| `pending` | `accepted` | переход в `accepted` |
| отсутствует | `accepted` | запрещённый переход |

Проверка участника выполняется до изменения состояния. `UpdatePair` атомарно
читает обе стороны пары, применяет переход и сохраняет изменение под одной
блокировкой; сетевой вызов выполняется вне этой блокировки.

## Лабораторная работа №3 — HTTP API

### Маршруты

Все бизнес-маршруты требуют заголовок `X-Demo-User`. Допустимы ID из
`[A-Za-z0-9_-]{1,32}`; в demo-фикстурах есть пользователи `u1`–`u6`.
Заголовок задаёт учебную идентичность, а не является production-аутентификацией.
Маршруты Discovery, Like и Pair не принимают JSON-тела; редактирование профиля
из LR4 использует JSON-тело.

| Метод и путь | Вход | Успех и DTO | Сценарий и правило |
| --- | --- | --- | --- |
| `GET /v1/me/discovery?interest=go&limit=2&offset=0` | Обязательный `interest`; `limit` по умолчанию 20, диапазон 1–50; `offset` по умолчанию 0, неотрицательный | `200 {"items":[{"id":"u2","interests":["go","music"]}],"limit":2,"offset":0}` | LR1 `Discover`, точный фильтр по интересу и сортировка ID |
| `PUT /v1/me/likes/{targetID}` | ID в пути, тело запрещено | `200 {"user_id":"u1","target_id":"u2","status":"pending","matched":false,"matched_now":false,"changed":true}` | LR2 `React`, проверка двух профилей через Profile API и атомарный переход |
| `GET /v1/me/pairs/{targetID}` | ID в пути, тело запрещено | `200 {"user_id":"u1","target_id":"u2","status":"none","matched":false,"matched_now":false,"changed":false}` при отсутствии реакций | LR2 `Inspect`, чтение того же состояния без записи |

Выдача фильтруется по интересу после правил LR1 и до пагинации; пустой
`interest`, неизвестный/повторённый параметр, неверное число, `limit > 50` и
отрицательный `offset` дают `400`. Фильтр точный, с учётом регистра. Выдача
сортируется по ID; Like сам по себе кандидата из discovery не исключает, так
как такого правила не было в LR1. Пустая страница всегда содержит `"items":[]`.

Команда проверяет активность обоих пользователей через Profile API до записи.
Повтор Like возвращает `changed:false`. При первой встречной реакции
`matched_now:true`; дальнейшее чтение показывает `matched:true`.

### Ошибки

Тело обработанной ошибки имеет общий формат:

```json
{"code":"target_not_found","message":"A required participant was not found"}
```

| Причина | HTTP | `code` |
| --- | ---: | --- |
| Неверные ID, identity, query или тело | 400 | `invalid_target_id`, `invalid_demo_identity`, `invalid_query`, `body_not_allowed` и др. |
| Не найден профиль в Profile API | 404 | `target_not_found` |
| Неактивный профиль | 403 | `participant_inactive` |
| Запрещённый переход | 409 | `invalid_transition` |
| Profile API вернул ошибку, неверный JSON или слишком большой ответ | 502 | `dependency_failure` |
| Истёк общий бюджет Profile API | 504 | `dependency_timeout` |
| Пара заблокирована | 409 | `user_blocked` |
| PostgreSQL не выполнил запрос в отведённый бюджет | 503 | `database_timeout` |
| PostgreSQL отклонил транзакцию для повтора | 503 | `transaction_retryable` |
| Ответ на COMMIT потерян, итог неизвестен | 503 | `commit_unconfirmed` |
| Неожиданная внутренняя ошибка | 500 | `internal_error` |

Причины сопоставляются через `errors.Is`, в том числе после обёртывания. Ответы
на неизвестные путь или метод — стандартные `ServeMux` 404/405. При отмене
клиентского запроса сервер прекращает зависимый HTTP-вызов; ответ по закрытому
соединению не гарантируется.

## Лабораторная работа №4 — транзакции PostgreSQL

### Маршруты и правила

Все маршруты основного API требуют `X-Demo-User`.
Владельцем профиля может быть только сам пользователь; редактируются интересы.

| Метод и путь | Вход | Успех и DTO | Правило |
| --- | --- | --- | --- |
| `PUT /v1/me/blocks/{targetID}` | ID в пути, тело запрещено | `200` DTO пары с `"blocked":true` | Блокировка постоянна и действует на пару; реакциям она не мешает остаться в истории |
| `GET /v1/profiles/{profileID}` | ID в пути, тело запрещено | `200 {"id":"u1","active":true,"interests":["go","backend"],"version":1}` | Чтение профиля и текущей версии |
| `PUT /v1/profiles/{profileID}` | `{"expected_version":1,"interests":["go","systems"]}` | `200` профиль с увеличенной версией | Изменение только владельцем и только при совпадении ожидаемой версии |

У всех Like и Block одна транзакционная точка сериализации — строка
`interaction_pairs` с каноническими `(user_low,user_high)`. Она блокируется
`SELECT ... FOR UPDATE`, и реакции, блокировка и Match записываются атомарно.
Если Like фиксируется первым, следующий Block деактивирует Match; если первым
фиксируется Block, ожидающий Like получает `409 user_blocked`. Блокировка
повторна и неизменяема; после неё новые Like для пары отклоняются.

Профиль обновляется под `SELECT ... FOR UPDATE`; запись увеличивает `version`
в той же транзакции. Из двух правок с одной версией успешно фиксируется только
одна, остальные получают `409 version_conflict` и должны перечитать профиль.

Схема в `internal/postgres/migrations/001_initial.sql` задаёт внешние ключи,
уникальность направленной реакции и пары Match, канонический порядок пары,
допустимые статусы, положительную версию и ограничения на блокирующего. При
старте приложение применяет миграцию под advisory lock и идемпотентно добавляет
демо-профили. Перезапуск не очищает данные.

При `commit_unconfirmed` нельзя слепо повторять команду: транзакция могла
зафиксироваться. Сначала прочитайте состояние пары или профиль. Ошибки
конфликта сериализации, deadlock и lock timeout сообщаются как
`transaction_retryable`; перечитайте состояние перед повтором.

### Profile API и управляемые отказы

Profile API запускается отдельно и слушает по умолчанию только
`127.0.0.1:8081`. Основное приложение использует переиспользуемый
`http.Client`, передаёт контекст команды, ограничивает время и читает не более
`PROFILE_RESPONSE_LIMIT_BYTES + 1` байт. Ограничение обнаруживает большой ответ,
а не принимает его усечённую часть за целый JSON.

| Режим | Ответ Profile API | Результат команды |
| --- | --- | --- |
| `ok` | Профиль или 404 для неизвестного ID | Обычная проверка активности |
| `missing` | 404 | `404 target_not_found`, без изменения пары |
| `error` | 500 | `502 dependency_failure`, без изменения пары |
| `slow` | Ожидание с поддержкой отмены | Обычно `504 dependency_timeout`, без изменения пары |
| `large` | JSON больше лимита клиента | `502 dependency_failure`, без изменения пары |

Режим устанавливается локальным служебным маршрутом, не являющимся API продукта:

```http
PUT http://127.0.0.1:8081/_admin/mode
Content-Type: application/json

{"mode":"error"}
```

### Сборка, конфигурация и остановка

Запустите из корня репозитория в отдельных терминалах:

```powershell
docker compose up -d --wait postgres
```

```powershell
go run ./cmd/profile-api
```

```powershell
go run ./cmd/app
```

Основное приложение слушает `:8080`. Profile API слушает `127.0.0.1:8081`.
PostgreSQL по умолчанию доступен на `localhost:5432` с локальными учётными
данными `linkup/linkup`. Для остановки приложения нажмите `Ctrl+C`; сервер
дожидается запросов до `SHUTDOWN_GRACE_MS`, затем принудительно закрывает
соединения. Для полного сброса локальных данных выполните
`docker compose down -v` (команда удаляет volume PostgreSQL).

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `APP_ADDR` | `:8080` | Адрес HTTP API |
| `PROFILE_API_URL` | `http://127.0.0.1:8081` | Base URL зависимости |
| `COMMAND_BUDGET_MS` | `900` | Общий бюджет команды и всех проверок |
| `PROFILE_HTTP_TIMEOUT_MS` | `700` | Timeout одного HTTP-запроса клиента |
| `PROFILE_RESPONSE_LIMIT_BYTES` | `4096` | Максимальный полный ответ зависимости (128–1,048,576) |
| `SHUTDOWN_GRACE_MS` | `5000` | Бюджет штатного завершения приложения |
| `PROFILE_API_ADDR` | `127.0.0.1:8081` | Адрес локального Profile API |
| `PROFILE_API_SLOW_MS` | `2000` | Задержка режима `slow` |
| `DATABASE_URL` | `postgres://linkup:linkup@localhost:5432/linkup?sslmode=disable` | URL PostgreSQL |
| `DB_QUERY_TIMEOUT_MS` | `700` | Общий бюджет обращения к PostgreSQL |
| `DB_LOCK_TIMEOUT_MS` | `400` | Бюджет ожидания блокировки транзакции |
| `DB_MAX_OPEN_CONNS` | `10` | Размер пула, от 2 до 100 |

Все timeout принимают значения от 1 мс до 24 ч; размер ответа должен быть от
128 до 1,048,576 байт. Некорректные значения останавливают запуск с ошибкой.
Серверы ограничивают заголовки, время чтения заголовков и idle-соединения.
Запросы журналируются через `slog` с request ID, методом, маршрутом, статусом
и длительностью; request ID возвращается в `X-Request-ID`. Тела запросов и
персональные данные в журнал не записываются.

### Воспроизводимые запросы

Полный набор запросов с ожидаемыми статусами находится в
[`requests.http`](requests.http). Ключевые команды:

```powershell
curl.exe -H "X-Demo-User: u1" "http://localhost:8080/v1/me/discovery?interest=go&limit=2&offset=0"
curl.exe -H "X-Demo-User: u1" "http://localhost:8080/v1/me/discovery?interest=go&limit=2&offset=2"
curl.exe -X PUT -H "X-Demo-User: u1" "http://localhost:8080/v1/me/likes/u2"
curl.exe -X PUT -H "X-Demo-User: u1" "http://localhost:8080/v1/me/likes/u2"
curl.exe -H "X-Demo-User: u1" "http://localhost:8080/v1/me/pairs/u2"
curl.exe -X PUT -H "X-Demo-User: u2" "http://localhost:8080/v1/me/likes/u1"
curl.exe -X PUT -H "X-Demo-User: u1" "http://localhost:8080/v1/me/blocks/u2"
curl.exe -H "X-Demo-User: u1" "http://localhost:8080/v1/profiles/u1"
curl.exe -X PUT -H "X-Demo-User: u1" -H "Content-Type: application/json" -d "{\"expected_version\":1,\"interests\":[\"go\",\"systems\"]}" "http://localhost:8080/v1/profiles/u1"
```

### Проверки и границы

```powershell
go test ./...
go vet ./...
go test -race ./...
go build ./...
$unformatted = gofmt -l .
if ($unformatted) { throw "Run gofmt on: $unformatted" }
```

Интеграционные тесты используют настоящий PostgreSQL, создают изолированную
схему, проверяют rollback, ограничения, конкурентные правки и оба порядка
ожидания Like/Block. Запустите их при доступном PostgreSQL:

```powershell
$env:TEST_DATABASE_URL = "postgres://linkup:linkup@localhost:5432/linkup?sslmode=disable"
go test -tags=integration ./...
```

GitHub Actions запускает этот набор с PostgreSQL service. Demo identity не
аутентифицирует пользователя; Profile API остаётся учебной внешней зависимостью
для проверки доступности участников, а источником данных профилей и
взаимодействий служит PostgreSQL.

| Маршрут | Переиспользованный контракт | Новая часть LR3 | Автор |
| --- | --- | --- | --- |
| Discovery | LR1 `Discover` | HTTP DTO, интерес-фильтр, сортировка и пагинация | Исполнитель Go-изменения (назначить в MR/PR) |
| PUT Like | LR2 `ProcessReaction`, `React` | Profile API, HTTP validation и handler | Исполнитель Go-изменения (назначить в MR/PR) |
| GET Pair | LR2 состояние пары | HTTP DTO и read-only handler | Исполнитель Go-изменения (назначить в MR/PR) |

Персональное распределение ответственности, ссылки на MR/PR и review должны
быть добавлены командой в описания задач/изменений: такие сведения не находятся
в исходных файлах проекта.
